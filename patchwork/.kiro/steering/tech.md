# Tech: Patchwork

Rules restated from `../.kiro/specs/patchwork-daily-mosaic/requirements.md` and `design.md` (paths here are relative to `patchwork/`). "Req 9.2" means Requirement 9, criterion 2; "D12" is an owner sign-off decision in design.md. If this file and requirements.md disagree, requirements.md wins and this file is updated and committed before the next work step (Req 29.7).

## Runtime: Node.js 24.18 or later

- Patchwork requires Node.js 24.18 or later; `package.json` declares `engines.node` ">=24.18.0" and `.nvmrc` names Node 24 (Req 1.4).
- On this machine the default `node` is v22.14.0, which is too old. Start every shell that runs Node with `export PATH="$HOME/.nvm/versions/node/v24.22.1/bin:$PATH"`.
- `npm test` and `npm run build` must pass on Node.js 24.18 (Req 1.4).

## Commands

Allowed deploy, upload and test commands, run from `patchwork/` (Req 1.5, Req 29.4). No other command that deploys, uploads or tests the app may be run:

| Command | Purpose |
|---|---|
| `npm run dev` | Devvit playtest in the owner's test subreddit. |
| `npm run deploy` | Private upload (the template's deploy script). |
| `devvit upload` | Private upload only. |
| `npm test` | `vitest --run`: every unit, property, integration and repository test in one run (Req 28.10). |
| `npm run build` | `tsc --build`, then `vite build`, then `node tools/check-bundle.mjs` (strict type check and bundle budget, D36). |

Forbidden commands (Req 1.6, Req 29.4):

- `npm run launch` (the template script runs `npm run deploy && devvit publish`; it is deleted in step 2).
- `devvit publish`.
- Any command that submits the app for review or makes the app public.

If a task would need one of them, leave it unrun, stop that task, and report the blocked step and the command to the owner (Req 1.6).

**`devvit login` is run only by the project owner**, in the owner's own terminal. If any step needs `devvit login` or another Reddit sign-in, stop and ask the owner, and resume only after the owner confirms (Req 1.7, Req 29.4). Project creation (the developers.reddit.com/new wizard or `npx devvit init`) also needs a browser sign-in, so the owner runs it in a scratch directory outside the workspace (D3).

Consequences of the five-command rule (L8, D35, D36):

- Do not run `devvit playtest`, `npx vitest`, `tsc`, `npm run size`, a lint command or the Lighthouse CLI as separate operations. Type checking and the bundle check run inside `npm run build`; repository checks run inside `npm test`.
- Lighthouse first contentful paint and open-to-input timing are measured by hand in Chrome DevTools, and results are recorded in `docs/verification.md`.
- `npm install`, `git` and plain `node` scripts that do not deploy, upload or test the app are not covered by the rule.

## Documentation-first API verification

- Before using any Devvit or Reddit API (function, hook, configuration key, CLI command or capability) in code for the first time, confirm it in the Devvit MCP server (`devvit_search`) or at https://developers.reddit.com/docs, and list the doc source in the step report (Req 1.1). No Devvit MCP server is configured in this workspace, so use the docs site and the installed type definitions.
- When the docs and memory disagree, the docs win; implement the documented behaviour and note the disagreement in the report (Req 1.2).
- If an API cannot be found in the docs, do not use it. Record it with the affected feature and use a documented alternative or a documented stub, saying which (Req 1.14).
- design.md lists the 35 doc facts (F1 to F35) this design relies on, each with its URL. Facts that change the request: no API edits a post title (B1); the cron time zone is undocumented (B2); `runAs: 'USER'` posts from the app account for non-owners while the app is unapproved (B3); Journeys records nothing until the app is allowlisted (B4); inline mode allows only tap or click (B11); `localStorage` is cleared on each app version (B12); realtime allows 100 messages per second per installation (B10).

## Free tiers only, zero LLM calls

- Use only services that cost nothing at the expected usage (Req 1.8). Zero paid API calls and zero LLM calls at runtime, at build time and in any scheduled job (Req 1.8).
- Mosaic art is generated by deterministic seeded procedural code, never by AI (Req 2.1). The Server and Shared_Logic make no outbound `fetch` to external services; the Client calls only `/api/` paths (repository check).

## Stack

- Devvit Web from the official React template: `@devvit/web`, `@devvit/start` and `devvit` 0.15.3, Hono server, React 19, Vite 8, TypeScript (versions from the template at creation time).
- Added in step 2: `vitest`, `@devvit/test`, `fast-check`, `@devvit/analytics`. Removed: Tailwind (D24), `public/snoo.png` (Req 2.8), the `launch` script.
- Hand-written CSS in one `tokens.css` with the Palette, theme tokens and one type scale.

## Code boundaries

- `src/shared/`: pure TypeScript (generator, slicer, solver, scoring, streak, Emoji_Grid, wire formats, API types). It never imports from `src/client/`, `src/server/`, `@devvit/*`, Redis or the Reddit API, and uses no `Math.random`, `Date` or locale functions, so results are identical on Client and Server in any time zone (Req 3.2, Req 28.2).
- `src/server/`: the Hono app; it owns every Redis and Reddit API call. `/api/*` routes serve the Client; `/internal/*` routes serve the Scheduler, Mod_Menu, forms, triggers and settings validation. Routes are thin; logic lives in `core/`.
- `src/client/`: the inline launch screen (`splash.html` + `splash.ts`, no framework, renders from `postData`) and the expanded game (`game.html` + `game.tsx`, React 19). The Pixel_Editor and the moderator review panel are lazy chunks.
- TypeScript `strict` in every tsconfig, plus `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`; 0 type errors (Req 28.1).

## Server authority and secrecy

- The Client submits its fill grid; the Validator compares the filled Cells with the stored Solution using Server data only (Req 11.1). Solve time and Mistakes are Server-recorded; Client-supplied times, Mistakes and scores are ignored (Req 13.7).
- Before a Stitch the Client receives Clues, Tile_Size, Tile_Index and the generation only. Pixels go out only for Tiles with a Solve_Count of at least 1, and a Tile's Solution mask only to the user who stitched it (Req 8.2, Req 9.9, Req 11.8, Req 18.9).
- `postData` is public and limited to 2 KB, so it holds only the stitched-Tile snapshot (Req 8.2, design.md F14).
- Moderator actions re-check permission on the Server every time and fail closed (Req 21.6, Req 22.5).
- Logs and analytics carry no usernames, user IDs, comment text, Solutions or fill grids (Req 24.6).

## Redis rules

- Keys are namespaced by Day_Key (`pw:d:{yyyy-mm-dd}:...`) and built from known values; no key scans, no plain sets or lists, no `hMGet` (design.md F7).
- Assignment_Counter: `incrBy(key, 1)` (Req 9.1). First_Stitcher: `hSetNX` (Req 12.2). Solve_Count and Help_Count: `hIncrBy`. Leaderboard: a sorted set per Day_Key. Time_Distribution: one global hash of buckets.
- Zero read-modify-write sequences on shared values outside an atomic command or a transaction (Req 9.7, Req 27.4). Transactions watch only per-user keys and run only for an accepted Stitch or an upvote.
- Every Redis call has a 2 s timeout; failures return a retryable error and leave recorded state unchanged (Req 9.12, Req 12.8, Req 27.9).
- Tiles are generated at most once per Day_Key and Regeneration_Seed (Req 27.6, Req 27.7). Per-user-day data expires after 14 days to stay under the 100 MB unpublished storage cap (D12).

## Performance budgets

- Client JavaScript: 130 KB gzipped in total, lazy chunks included, and 15 KB gzipped for the launch screen; `tools/check-bundle.mjs` fails the build above either (Req 27.3, D10).
- First contentful paint within 1.5 s (Lighthouse mobile, Moto G Power class, 4G) and first Cell input within 3 s of opening (Req 27.1, Req 27.2, Req 10.1).
- The Mosaic is drawn on a single canvas (Req 18.1). The Solver checks a 7×7 Tile in under 50 ms and the Slicer handles a 7×7 Mosaic in under 5 s (Req 4.4, Req 4.10, Req 5.5).

## Tests

- Vitest with `@devvit/test` (`createDevvitTest` from `@devvit/test/server/vitest`) for Server tests against an in-memory Redis with transactions; Reddit API calls the harness lacks (such as Flair) are mocked.
- fast-check property tests with at least 100 runs each (`PBT_RUNS = 100`), each tagged `// Feature: patchwork-daily-mosaic, Property N: <name>`.
- Required tests: 120 consecutive Day_Keys from 2026-11-30 with all 7,680 Tiles uniquely solvable and the weekly difficulty curve; concurrent assignment with at least 100 users; concurrent Stitches of one Tile; the Validator cases; determinism, clue round-trip and Emoji_Grid properties; all passing in one `vitest --run` (Req 28.3 to Req 28.10).
- Measured values (bundle sizes, Lighthouse, timings, console-error runs) are recorded in `docs/verification.md` with date, method and commit.
